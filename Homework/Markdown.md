# 과제-02 : 배열 구현 vs 포인터(연결) 구현 비교

## 1. 메모리 사용량 비교

### 1.1 측정 방법

- 동일하게 7개의 노드를 갖는 이진트리를 **일반 이진트리 / 완전 이진트리 / 편향 이진트리** 세 가지 형태로 준비한다.
- 배열 구현은 `sizeof(ArrayTree)`를 이용하여 배열 기반 이진트리 구조체의 메모리 사용량을 측정한다.
- 포인터 구현은 `노드 수 × sizeof(Node)`를 기준으로 실제 생성된 노드의 메모리 사용량을 측정한다.
- `sizeof()` 값은 실행 환경에 따라 달라질 수 있으므로, 직접 컴파일하여 실행한 결과를 캡처해서 첨부한다.

### 1.2 실험에 사용한 트리

#### 일반 이진트리

입력:

`A(B(D,E),C(,F(,G)))`

구조:

```text
        A
       / \
      B   C
     / \   \
    D   E   F
             \
              G
```

#### 완전 이진트리

입력:

`A(B(D,E),C(F,G))`

구조:

```text
        A
       / \
      B   C
     / \ / \
    D  E F  G
```

#### 편향 이진트리

입력:

`A(,B(,C(,D(,E(,F(,G))))))`

구조:

```text
A
 \
  B
   \
    C
     \
      D
       \
        E
         \
          F
           \
            G
```

|---|---|---|---|
| 일반 이진트리 | 7 | 200bytes | 168bytes |
| 완전 이진트리 | 7 | 200bytes | 168bytes |

### 1.4 분석

배열 구현은 노드를 배열의 인덱스를 이용하여 저장하기 때문에, 실제 노드 수뿐만 아니라 트리의 모양에 따라 필요한 배열 공간이 달라질 수 있다.

0부터 시작하는 배열을 사용하는 경우 부모와 자식 노드의 위치는 다음과 같이 계산한다.

- 왼쪽 자식 = 2i + 1
- 오른쪽 자식 = 2i + 2
- 부모 = (i - 1) / 2

**완전 이진트리**: 노드가 배열의 앞부분에 빈 공간 없이 배치되기 때문에 배열의 공간을 효율적으로 사용할 수 있다. 또한 현재 구현에서는 노드 데이터를 char로 저장하기 때문에 노드 하나당 데이터 저장 공간이 작다는 장점이 있다.

**편향 이진트리**: 한쪽으로만 자식이 이어지는 경우 노드의 배열 인덱스가 빠르게 증가한다. 예를 들어 오른쪽으로 편향된 7개의 노드는 0 → 2 → 6 → 14 → 30 → 62 → 126과 같이 배치될 수 있다. 따라서 실제 노드는 7개이지만 배열의 더 많은 공간을 필요로 하게 된다.

**일반 이진트리**: 트리의 구조에 따라 배열의 빈 공간이 발생할 수 있으며, 완전 이진트리보다 공간 활용도가 낮아질 수 있다.

포인터(연결) 구현은 실제로 존재하는 각 노드를 동적으로 생성하여 연결하기 때문에 트리의 모양과 관계없이 실제 노드 수에 비례하여 메모리를 사용한다.

포인터 기반 노드는 data, left, right로 구성되므로 배열의 한 칸보다 많은 메모리를 사용하지만, 트리의 구조가 편향되어도 사용하지 않는 배열 공간이 발생하지 않는다는 장점이 있다.

### 1.5 결론

배열 구현은 특히 완전 이진트리처럼 노드가 빈틈없이 배치되는 경우 공간을 효율적으로 사용할 수 있다.

반면 트리가 편향되거나 불규칙한 형태가 되면 배열의 사용하지 않는 공간이 증가할 수 있다.

포인터 구현은 실제 존재하는 노드만 동적으로 생성하므로 트리의 형태와 관계없이 실제 노드 수에 비례하여 메모리를 사용한다.

따라서 트리의 형태가 완전 이진트리에 가까운 경우에는 배열 구현이 유리할 수 있고, 트리의 구조가 불규칙하거나 편향될 가능성이 있는 경우에는 포인터 구현이 공간 활용 측면에서 유리할 수 있다.

## 2. 자식 / 부모 / 형제 노드 탐색 비교

### 2.1 프로그램 설명

특정 노드 값을 입력받아 해당 노드의 자식, 부모, 형제 노드를 출력하는 기능을 두 구현에 각각 작성한다.

**배열 구현**

0부터 시작하는 배열에서 노드의 인덱스를 i라고 하면 다음과 같이 부모와 자식의 위치를 계산할 수 있다.

- 왼쪽 자식 = 2i + 1
- 오른쪽 자식 = 2i + 2
- 부모 = (i - 1) / 2

따라서 노드의 인덱스를 알고 있다면 부모와 자식의 위치를 계산하여 바로 접근할 수 있다.

- 왼쪽 자식 찾기: O(1)
- 오른쪽 자식 찾기: O(1)
- 부모 찾기: O(1)
- 형제 찾기: O(1)

단, 입력받은 노드의 값을 이용하여 해당 노드의 인덱스 자체를 찾는 과정은 배열을 탐색해야 하므로 **O(n)**이 필요하다.

**포인터(연결) 구현**

포인터 구현에서는 각 노드가 left, right 포인터를 가지고 있기 때문에 자식 노드는 바로 접근할 수 있다.

- 왼쪽 자식 찾기: O(1)
- 오른쪽 자식 찾기: O(1)

하지만 현재 구현에서는 parent 포인터를 저장하지 않기 때문에 특정 노드의 부모를 찾으려면 루트부터 트리를 탐색해야 한다.

따라서 부모와 형제 노드를 찾는 과정은 최악의 경우 **O(n)**이 필요하다.

또한 노드의 값을 이용하여 특정 노드를 찾는 과정 역시 트리를 탐색해야 하므로 **O(n)**이 필요하다.

### 2.2 실험에 사용한 트리

입력:

`A(B(D,E),C(,F))`

구조:

```text
        A
       / \
      B   C
     / \   \
    D   E   F
```

검색할 노드:

`E`

예상 결과:

- 부모: B
- 자식: 없음
- 형제: D

### 2.4 효율성 비교 분석

| 연산 | 배열 구현 | 포인터 구현 |
|---|---|---|
| 자식 찾기 | O(1) | O(1) |
| 부모 찾기 | O(1) | O(n) |
| 형제 찾기 | O(1) | O(n) |
| 값으로 노드 위치 찾기 | O(n) | O(n) |

배열 구현에서는 노드의 인덱스를 알고 있을 경우 2i + 1, 2i + 2, (i - 1) / 2와 같은 계산을 이용하여 부모와 자식의 위치를 바로 확인할 수 있다.

반면 포인터 구현에서는 자식은 left, right 포인터를 통해 바로 접근할 수 있지만, 현재 구현에서는 부모 포인터가 없기 때문에 부모를 찾기 위해 루트부터 탐색해야 한다.

형제 노드 역시 부모를 확인한 후 다른 자식 노드를 찾아야 하므로 탐색이 필요하다.

따라서 노드의 인덱스를 알고 있는 경우 부모와 형제 노드에 대한 접근은 배열 구현이 더 효율적이다. 반면 포인터 구현은 트리의 구조가 불규칙하거나 편향되어도 실제 노드만 동적으로 관리할 수 있다는 장점이 있다.

## 3. 배열 기반 구현과 포인터 기반 구현의 종합 비교

| 비교 항목 | 배열 기반 구현 | 포인터 기반 구현 |
|---|---|---|
| 메모리 할당 | 배열에 미리 공간 할당 | 노드마다 동적 할당 |
| 노드 접근 | 배열 인덱스로 접근 | 포인터를 따라 접근 |
| 부모 접근 | 인덱스 계산으로 가능 | parent 포인터가 없으면 탐색 필요 |
| 자식 접근 | 인덱스 계산으로 가능 | left, right 포인터로 접근 |
| 완전 이진트리 | 공간 활용에 유리 | 실제 노드만 저장 |
| 편향 이진트리 | 빈 공간이 발생할 수 있음 | 실제 노드만 저장 |
| 구현 난이도 | 비교적 단순함 | 동적 메모리 관리 필요 |
| 메모리 관리 | 배열 크기에 제한을 받음 | 필요한 노드를 동적으로 생성 및 삭제 |

## 4. 최종 결론

배열 기반 이진트리는 노드의 위치를 배열 인덱스로 표현하기 때문에 부모와 자식의 위치를 계산하기 쉽다. 특히 완전 이진트리에서는 노드가 배열의 앞부분에 밀집되어 저장되므로 공간을 효율적으로 사용할 수 있다.

반면 편향 이진트리에서는 노드의 인덱스가 빠르게 증가하여 실제 노드 수보다 많은 배열 공간을 필요로 할 수 있다.

포인터 기반 이진트리는 실제 존재하는 노드를 동적으로 생성하기 때문에 트리의 형태와 관계없이 필요한 노드만 저장할 수 있다. 따라서 불규칙하거나 편향된 트리에서도 배열의 빈 공간으로 인한 낭비가 발생하지 않는다.

또한 부모 포인터를 사용하지 않는 현재 구현에서는 배열 기반 구현이 노드의 부모와 형제를 찾는 데 인덱스 계산을 이용할 수 있어 효율적이다. 포인터 기반 구현은 부모를 찾기 위해 루트부터 탐색해야 한다.

결과적으로 두 구현 방식은 각각 장단점이 있으며, 트리의 형태와 필요한 연산에 따라 적절한 구현 방식을 선택할 수 있다.
