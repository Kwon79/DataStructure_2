# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 1. 구현 개요

- 데이터 크기 n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 각 n마다 무작위 정수(중복 허용) 원본 배열을 한 번 생성하고, 5가지 정렬이 모두 **동일한 원본의 복사본**을 사용한다.
- 모든 정렬 후 오름차순 정렬 여부를 검사하며, 이상이 있으면 출력 행 끝에 `[정렬 오류!]`가 표시된다.
- 힙 정렬은 입력 배열 자체를 최대 힙으로 사용하고, 병합 정렬은 임시 배열 1개를 사용한다. 퀵 정렬은 Lomuto 분할에 피벗 선택 방식(첫 원소 / 무작위 / 세 원소 중앙값)만 바꿔서 실험했다.

## 2. 측정 방법

**비교 횟수**
- 데이터 값끼리 비교하는 모든 지점에서 카운터를 증가시켰다(`less()`, `less_eq()` 함수).
- 힙 정렬은 힙 구성과 힙 속성 복구(`sift_down`)의 비교를 모두 포함한다. 자식 둘 중 큰 쪽을 고르는 비교와, 그 자식을 부모와 비교하는 비교가 각각 센다.
- 퀵 정렬은 분할 과정의 비교와 중앙값 선택(Median-of-Three)의 비교를 포함한다. 반복문 인덱스 검사와 종료 조건 검사는 제외했다.

**메모리 사용량 (직접 계산)**

원본 배열은 공통 비용이므로 제외하고, 정렬 중 추가로 필요한 공간만 계산했다. x64 기준 `sizeof(int)=4`, `sizeof(포인터)=8`이다.

- 함수 한 번 호출의 크기 = 매개변수와 지역변수의 `sizeof` 합 + 반환 주소(8B)
- 재귀 함수는 실행 중 **기록한 최대 재귀 깊이** × 프레임 크기로 계산했다.

| 알고리즘 | 계산식 |
|---|---|
| 힙 정렬 | 재귀 없음. 보조 변수 + `sift_down` 프레임 = **40B (n과 무관)** |
| 병합 정렬 | 임시 배열 `n × 4B` + (최대 깊이 × 36B) + `merge()` 프레임 48B |
| 퀵 정렬 | (최대 깊이 × 28B) + `partition()` 프레임 48B |

예) 병합 정렬 n=20,000: 최대 깊이 16 → 80,000 + 16×36 + 48 = **80,624B** (출력값과 일치)

## 4. 분석

### 4.1 데이터 크기 증가에 따른 비교 횟수

n이 1,000에서 20,000으로 20배 늘 때 비교 횟수는 힙 정렬이 약 30배(16,830 → 510,611), 병합 정렬이 약 30배(8,715 → 260,891)로 늘었다. n log n 증가율은 20 × (log₂20000 / log₂1000) ≈ 28.7배이므로, 세 알고리즘 모두 n²이 아니라 n log n 증가 양상을 보였다.

n=20,000에서 n·log₂n ≈ 285,754와 비교하면 다음과 같다.

- **병합 정렬 (약 0.91배)**: 배열을 항상 절반으로 나누므로 분할이 균형 잡혀 있고, 병합 과정에서 한쪽이 먼저 바닥나면 남은 원소는 비교 없이 복사하기 때문에 비교 횟수가 가장 적다.
- **퀵 정렬 (약 1.1~1.2배)**: 분할이 완벽하게 반반으로 나뉘지 않아 병합 정렬보다 비교가 많다.
- **힙 정렬 (약 1.8배)**: `sift_down`이 한 단계 내려갈 때마다 "자식 둘 중 큰 쪽 선택"과 "그 자식과 부모 비교"를 합쳐 비교를 2번 수행한다. 이 때문에 병합 정렬의 약 2배(510,611 / 260,891 ≈ 1.96)에 가깝게 나왔다.

### 4.2 실행시간

n=20,000에서 힙 정렬(0.76ms)이 가장 빨랐고 퀵 정렬(1.05~1.37ms)과 병합 정렬(1.32ms)이 뒤를 이었다. 모든 데이터 크기에서 힙 정렬이 가장 짧았다.

**비교 횟수는 힙 정렬이 가장 많은데 시간은 가장 짧았다.** 실행시간은 비교 횟수만으로 결정되지 않고 데이터 이동과 메모리 접근 비용도 포함하기 때문이다.

- 힙 정렬은 배열 안에서 값을 한 칸씩 끌어올리고 마지막에 한 번 쓰는 방식(`sift_down`)이라 추가 복사가 없다.
- 병합 정렬은 병합할 때마다 임시 배열에 쓴 뒤 원본 배열로 다시 복사하므로, 비교는 적어도 원소 이동이 레벨마다 2n번 발생한다. 임시 배열 할당도 시간에 포함된다.
- 퀵 정렬은 제자리 정렬이지만 분할 과정에서 교환이 많고 재귀 호출 비용이 든다.

즉 이번 실험에서는 비교 횟수의 이점이 병합 정렬의 데이터 이동 비용에 상쇄되었다. 다만 이 순위는 정수 배열, 이 컴퓨터, 이 구현 기준이므로 일반화하기는 어렵다. 또한 n이 작을 때는 시간 값이 매우 작아(0.03~0.3ms) 측정 오차의 영향이 크다.

### 4.3 메모리 사용량

| 알고리즘 | n=1,000 | n=20,000 | 증가 양상 |
|---|---|---|---|
| 힙 정렬 | 40B | 40B | 변화 없음 |
| 병합 정렬 | 4,444B | 80,624B | n에 비례 (약 18배) |
| 퀵 정렬 | 524~748B | 776~1,056B | 매우 완만 (약 1.4배) |

- **힙 정렬**은 입력 배열을 그대로 힙으로 사용하고 재귀도 쓰지 않아 보조 변수만 필요하므로 O(1)이다.
- **병합 정렬**은 병합 결과를 담을 임시 배열이 필요해 n × 4B가 대부분을 차지한다(n=20,000에서 80,000B / 80,624B). 재귀 스택 몫은 600B 정도에 불과하다.
- **퀵 정렬**은 임시 배열이 없고 재귀 스택만 쓴다. 분할이 비교적 균형 잡혀 재귀 깊이가 log n 수준으로 유지되므로 n이 20배 늘어도 메모리는 약 1.4배만 늘었다.

### 4.4 퀵 정렬의 피벗 선택 방법

| n | First | Random | Median3 |
|---|---|---|---|
| 1,000 | 10,513 | 10,250 | 10,964 |
| 4,000 | 54,457 | 55,599 | 54,608 |
| 8,000 | 111,963 | 124,313 | 113,353 |
| 16,000 | 259,612 | 260,199 | 242,578 |
| 20,000 | 347,602 | 326,820 | 321,880 |

- 무작위 데이터에서는 세 방식의 비교 횟수 차이가 크지 않았고, 크기마다 가장 적은 방식이 달라졌다. 데이터가 이미 무작위이므로 첫 원소도 사실상 무작위 피벗과 같은 효과를 내기 때문이다.
- n이 큰 구간(16,000, 20,000)에서는 Median3의 비교 횟수가 가장 적었다. 세 값의 중앙값은 극단적으로 크거나 작은 값이 피벗이 될 가능성을 줄여 분할을 더 균형 있게 만든다.
- Median3는 피벗마다 비교를 2~3번 추가하지만, 분할이 좋아지는 효과가 이를 상쇄하거나 앞섰다.
- Random은 분할이 좋아도 피벗마다 `rand()` 호출이 필요해서 시간이 대체로 First나 Median3보다 길었다(n=8,000, 16,000, 20,000).
- 이 차이는 **무작위 데이터에서는 작지만**, 이미 정렬되었거나 역순인 데이터에서는 첫 원소 선택이 매번 한쪽으로만 나뉘어 O(n²)로 나빠진다. 이번 실험에서는 측정하지 않았고, 이론적으로 Random과 Median3가 이 상황을 막아 준다.

### 4.5 시간 복잡도와 공간 복잡도

| 알고리즘 | 시간(평균) | 시간(최악) | 공간 | 실험에서 확인된 점 |
|---|---|---|---|---|
| 힙 정렬 | O(n log n) | O(n log n) | O(1) | 비교 많음, 메모리 고정, 시간은 가장 짧음 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n) | 비교 가장 적음, 메모리 n에 비례 |
| 퀵 정렬 | O(n log n) | O(n²) | O(log n) (평균) | 비교 중간, 메모리 적음, 피벗에 따라 성능 변동 |

## 5. 결론

- 비교 횟수만 보면 병합 정렬이 가장 효율적이지만, 실제 실행시간은 데이터 이동과 임시 배열 사용 때문에 힙 정렬이 가장 빨랐다.
- 메모리는 힙 정렬이 가장 적고, 퀵 정렬은 재귀 스택만 쓰며, 병합 정렬은 n에 비례한 추가 공간이 필요했다.
- 퀵 정렬의 피벗 선택 차이는 무작위 데이터에서는 크지 않지만, Median3가 큰 n에서 비교 횟수가 가장 적어 안정적인 선택으로 보인다.
- 따라서 "비교 횟수가 적은 알고리즘이 반드시 빠른 것은 아니며", 추가 메모리와 데이터 이동까지 함께 고려해서 알고리즘을 선택해야 한다.
