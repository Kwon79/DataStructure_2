# 과제 15: 퀵 정렬과 AVL 트리 정렬의 성능 비교

## 1. 구현 개요|

- 데이터 크기 n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000, 값 범위는 0 ~ 999,999(중복 허용)이다.
- 각 n마다 원본 데이터와 삽입/삭제 연산 목록(n의 20%)을 **한 번 생성**하고, 퀵 정렬 배열과 AVL 트리에 **같은 데이터와 같은 연산 순서**를 적용했다.
- 연산 규칙: 난수가 짝수면 삽입, 홀수면 삭제이고, 삽입/삭제할 값은 별도의 난수이다. 삭제할 값이 없으면 건너뛴다.

**퀵 정렬**
- 피벗 선택 방법은 **세 원소의 중앙값(Median-of-Three)** 을 사용했다. 분할은 Lomuto 방식이다.
- 삽입: 정렬된 배열을 앞에서부터 선형 탐색해 처음으로 값 이상인 위치를 찾고, 그 뒤의 데이터를 한 칸씩 뒤로 이동한 뒤 저장한다.
- 삭제: 선형 탐색으로 같은 값을 찾고(찾기 전에 더 큰 값을 만나면 없는 것으로 판단), 뒤의 데이터를 앞으로 한 칸씩 이동한다. 같은 값이 여러 개면 처음 발견한 한 개만 제거한다.

**AVL 트리 정렬**
- 원본 데이터를 AVL 트리에 하나씩 삽입해 정렬 상태를 유지하고, 필요하면 LL/RR/LR/RL 회전으로 균형을 복구한다.
- 중복 값은 노드의 `count`에 개수를 저장한다. 삽입 시 같은 값을 만나면 `count`를 증가시키고, 삭제 시 `count`가 2 이상이면 감소시킨다. `count`가 1이면 노드를 제거한다.
- 노드를 제거할 때 자식이 둘이면 오른쪽 서브트리의 최솟값 노드를 떼어 그 자리에 연결한다(값 복사 없이 포인터만 변경).
- 중위 순회로 오름차순 결과를 확인했다.

**검증**: 정렬 직후와 모든 연산 후에 (1) 오름차순인지, (2) 두 자료구조의 최종 데이터가 개수와 값 모두 동일한지 확인했다. 모든 크기에서 `Verification : OK`가 출력되었다.

## 2. 측정 방법

**실행 환경**: Visual Studio, **Release x64**, 실행(`Ctrl+F5`).

**총 수행시간**
- `QueryPerformanceCounter`로 측정하고 단위는 ms이다. 퀵 정렬은 정렬 시작부터 모든 삽입·삭제 완료까지, AVL은 트리 구성(삽입) 시작부터 모든 삽입·삭제 완료까지이다.
- 난수 생성, 원본 배열 복사, 정렬 결과 검증(중위 순회 포함), 결과 출력 시간은 제외했다. 모든 값은 동일한 방식으로 측정했다.

**비교 횟수**
- 데이터 값끼리 비교하는 모든 지점에서 카운트했다. 퀵 정렬은 분할 비교와 중앙값 선택 비교, 삽입 위치·삭제 대상 탐색 비교를 포함한다. AVL은 삽입·삭제 때 경로의 노드와 키를 비교한 횟수이다.
- 3-way 비교(`<`, `=`, `>`를 한 번에 판단) 호출 1회를 비교 1회로 계산했다.
- 반복문 인덱스 검사, 균형 인수와 높이 계산 같은 데이터 값과 무관한 비교는 제외했다.

**데이터 이동 횟수**
- 배열: 값 하나를 대입하면 1회이다. 교환(swap)은 임시 변수를 거치는 대입 3회로 계산했다. 삽입·삭제 시 밀기/당기기와 새 값 저장도 대입 1회씩 센다.
- AVL: 새 노드에 키 값을 저장할 때만 1회로 계산했다. 포인터 연결 변경, 회전, `count`와 높이 갱신은 제외했다.

**메모리 사용량 (직접 계산, x64 기준)**
- 자료구조 크기 + 재귀 호출 스택(최대 깊이 × 프레임 크기)으로 계산했다. 프레임 크기는 매개변수와 지역변수의 `sizeof` 합에 반환 주소(8B)를 더했다. 최대 재귀 깊이는 실행 중 기록했다.

| 방법 | 계산식 |
|---|---|
| 퀵 정렬 | 배열 `4B × (n + 연산 수)` + (최대 깊이 × 28B) + `partition()` 프레임 56B |
| AVL 트리 | (최대 노드 수 × 32B) + 루트 포인터 8B + (최대 깊이 × 36B) + 회전 프레임 40B |

- AVL 노드는 `key`(4B), `count`(4B), `height`(4B), 정렬을 위한 패딩 4B, 포인터 2개(16B)로 **32B**이다.
- 퀵 정렬 배열은 삽입 공간까지 미리 할당한 크기를 사용했다. 예) n=20,000: 4 × 24,000 = 96,000B에 스택 약 700B를 더해 96,728B이다.

## 4. 분석

### 4.1 총 수행시간과 비교 횟수

| n | 시간 비 (Quick / AVL) | 비교 횟수 비 (Quick / AVL) |
|---|---|---|
| 1,000 | 0.75배 | 약 11배 |
| 2,000 | 1.6배 | 약 18배 |
| 4,000 | 2.5배 | 약 32배 |
| 8,000 | 4.0배 | 약 57배 |
| 16,000 | 8.1배 | 약 108배 |
| 20,000 | 9.9배 | 약 134배 |

비교 횟수는 모든 크기에서 AVL이 훨씬 적었고, n이 커질수록 차이가 벌어졌다. 이유는 두 방법의 연산 구조가 다르기 때문이다.

- **퀵 정렬 쪽의 비용은 대부분 삽입·삭제에서 나온다.** 정렬 자체는 n log n 수준(n=20,000에서 약 30만 회)인데, 정렬된 배열에서 선형 탐색을 하므로 연산 1회마다 평균 n/2개 정도를 비교한다. n=20,000에서 연산 4,000회 × 약 10,000회 ≈ 4,000만 회로, 전체 4,305만 회의 대부분이다.
- **AVL은 연산마다 트리 높이(약 log n)만큼만 비교한다.** 전체 32만 회 중 대부분은 초기 트리 구성(n회 삽입 × 깊이)이고, 삽입·삭제 구간의 비용은 작다.

시간의 차이(9.9배)는 비교 횟수의 차이(134배)보다 훨씬 작았다. 배열의 선형 탐색은 연속된 메모리를 순서대로 읽어 캐시 효율이 좋고 비교 하나가 매우 가볍다. 반면 AVL은 노드마다 `malloc`으로 흩어진 메모리를 포인터로 따라가고, 회전과 높이 갱신 같은 추가 작업이 있어 비교 1회당 비용이 크다. 따라서 **비교 횟수 차이가 그대로 시간 차이가 되지는 않는다.**

n=1,000에서는 퀵 정렬 방식(0.102ms)이 AVL(0.137ms)보다 빨랐다. 데이터가 작으면 배열 전체가 캐시에 들어가 선형 탐색이 매우 빠르고, AVL은 노드 1,000개를 할당하고 균형을 맞추는 비용이 상대적으로 크기 때문이다. 두 방법의 시간은 n=1,000과 2,000 사이에서 역전되었다.

### 4.2 데이터 이동 횟수

데이터 이동은 가장 큰 차이를 보였다. n=20,000에서 퀵 정렬 방식 약 2,175만 회, AVL 약 2.2만 회로 **약 1,000배** 차이다.

- **배열**: 삽입할 때마다 삽입 위치 뒤의 원소를 모두 한 칸씩 밀어야 한다. n=20,000에서 삽입 약 2,000회 × 평균 약 1만 개 ≈ 2,000만 회로, 전체 이동의 대부분이다. 정렬 자체의 이동(약 수십만 회)은 비중이 작다.
- **AVL**: 새 노드를 만들 때 값을 한 번 저장할 뿐, 위치를 만들기 위해 다른 데이터를 옮기지 않는다. 이동은 초기 구성 n회와 삽입 횟수에 해당하는 약 2만 회로, 사실상 "저장한 값의 개수"와 같다.
- 삭제는 이번 실험에서 대부분 실패했다(5.의 참고 참조). 값을 찾아 지우는 경우가 많았다면 배열의 이동 횟수는 더 늘어났을 것이다.

### 4.3 메모리 사용량

| n | 퀵 정렬(배열) | AVL | AVL / 배열 |
|---|---|---|---|
| 1,000 | 5,388B | 35,716B | 약 6.6배 |
| 20,000 | 96,728B | 695,832B | 약 7.2배 |

- **배열**은 값만 저장하므로 원소당 4B이고, 재귀 스택(약 700B)을 더해도 전체 크기가 작다.
- **AVL**은 원소(노드)당 32B가 필요하다. 값 4B 외에 `count`, 높이, 왼쪽/오른쪽 포인터가 노드마다 붙기 때문이다. 같은 개수의 데이터를 저장할 때 약 7배의 메모리를 쓴다.
- 두 방법 모두 데이터 개수에 비례해 메모리가 늘었다(n이 20배일 때 배열 약 18배, AVL 약 19배). 재귀 스택은 둘 다 깊이가 log n 수준이라 전체에서 차지하는 비중이 작았다.

### 4.4 데이터 크기 증가에 따른 변화

n이 1,000에서 20,000으로 20배 늘었을 때의 증가 배수는 다음과 같다. (n log n이면 약 29배, n²이면 400배)

| 항목 | Quick(배열) | AVL |
|---|---|---|
| 시간 | 약 266배 | 약 20배 |
| 비교 횟수 | 약 355배 | 약 30배 |
| 데이터 이동 | 약 313배 | 약 20배 |
| 메모리 | 약 18배 | 약 19.5배 |

- 배열 방식은 시간·비교·이동이 모두 n²에 가까운 증가를 보였다. 연산 횟수(n의 20%)와 탐색/이동 길이(n에 비례)가 둘 다 n에 비례해 커지기 때문이다.
- AVL은 n log n 증가율(약 29배)과 비슷하거나 그 이하로 증가했다. 비교와 시간은 데이터 크기가 커져도 완만하게 늘어난다.
- 그래서 n이 커질수록 시간 비가 0.75배(AVL이 느림)에서 9.9배(AVL이 빠름)로 벌어졌다.
- 메모리는 둘 다 n에 비례해 증가했고 비율(약 7배)은 거의 일정했다.

### 4.5 삽입·삭제가 반복되는 환경에서 유리한 자료구조

**AVL 트리가 유리하다.**

- 정렬된 배열은 "탐색은 빠르지만(이진 탐색 가능) 삽입·삭제가 O(n)"이다. 위치를 찾는 것도 이번 실험처럼 선형이면 O(n)이고, 위치를 만들기 위한 이동도 O(n)이다.
- AVL은 탐색, 삽입, 삭제가 모두 O(log n)이고, 회전을 통해 데이터가 어떤 순서로 들어와도 높이를 log n으로 유지한다. 이동이 필요 없다.
- 실험에서 n=20,000일 때 비교 횟수는 134배, 데이터 이동은 1,000배 적었고 시간은 약 10배 짧았다. 연산이 많고 데이터가 클수록 이 차이는 더 커진다.

**배열이 나은 경우**도 있다.
- 데이터가 작거나(이번 실험의 n=1,000) 삽입·삭제가 드물고 조회가 주된 경우, 연속된 메모리 덕분에 단순하고 빠르다.
- 메모리를 아껴야 하는 경우에는 원소당 4B인 배열이 AVL(32B)보다 훨씬 적게 쓴다.

## 5. 결론 및 참고

- 삽입·삭제가 반복되는 환경에서는 배열의 선형 탐색과 데이터 이동 비용이 데이터 크기에 비례해 커져서 AVL 트리가 비교, 이동, 시간 모두 크게 유리했다. 대신 AVL은 노드마다 추가 정보가 필요해 메모리를 약 7배 썼다.
- 데이터가 작을 때는 배열이 오히려 빨랐고, 두 방법의 시간은 n=1,000과 2,000 사이에서 역전되었다. 따라서 자료구조 선택은 데이터 크기, 연산 비율, 메모리 제약을 함께 고려해야 한다.
- **참고(삭제 성공률)**: 삭제할 값을 0 ~ 999,999 범위의 새 난수로 뽑았기 때문에, 삭제가 실제로 성공하는 경우는 드물었다. 예를 들어 n=20,000에서 삭제를 약 2,000번 시도했지만 최종 개수가 21,969로 삽입 횟수만큼(약 2,000개)에 가깝게 늘었다. 이 경우 삭제는 "탐색 후 실패"로 끝나는 경우가 대부분이라, 삭제 시 데이터 이동 비용은 이번 결과에 거의 반영되지 않았다.
